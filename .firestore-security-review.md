# Firestore security review (prototype)

The configured Firebase project is `technoplus-eb80f` and the app targets its `(default)` Firestore database. Firebase CLI confirmed the database is Firestore Native, Standard edition, in `asia-south1`. The new rules passed local Firestore Emulator syntax validation and were released to the project's live Firestore database on 2026-10-25. Production authorization behavior for the existing admin role was not exercised end-to-end.

## Data and query map

- `projects`, `categories`, `clients`, `testimonials`, `homeExpertise`, `aboutTourism`: public site subscribes with `where('published', '==', true)`. Admin subscribes to each full collection ordered by `order`.
- `siteSections/homeExpertise`: one public/admin document subscription contains only the section name, heading, and description.
- `inquiries`: public form creates one bounded message with `status: 'new'` and server timestamp. Admin lists by descending `createdAt`, updates status and may delete.
- `adminUsers/{uid}`: signed-in user gets only their own role document. The trusted project owner provisions `enabled: true` out of band; all client writes and list access are denied.
- `homeExpertise` item docs contain only title/name, location, description, Cloudinary photo URL, published state, order, and timestamps.
- `aboutTourism` item docs contain only name, location, description, Cloudinary photo URL, published state, order, and timestamps. An admin-only `siteSections/aboutTourismSeed` marker prevents deleted destinations from being reseeded.
- All unlisted collections are denied by the catch-all rule.

## Threat checks

- Anonymous reads of drafts and all inquiry documents are denied. Public content reads are intentionally limited to published documents, and the public query includes the same published filter.
- Admin writes require Firebase Auth and a pre-provisioned enabled role document. Client rules cannot create, change, enumerate, or delete role documents.
- Content schemas use allow-lists, required fields, field types, and string/count bounds. Updates preserve `createdAt`.
- Homepage expertise items use bounded strings, a secure Cloudinary photo URL, and the same create/update validator. Section configuration accepts only bounded name, heading, and description strings.
- About tourism items use bounded name, location and description fields, a secure Cloudinary photo URL, a validated numeric order, and matching create/update validators.
- The tourism defaults marker is admin-only and cannot be deleted by client rules, so deleting the last destination does not cause defaults to return.
- Public inquiry creation validates field bounds and email shape, requires a server timestamp, and forces initial status to `new`. Anonymous updates and deletes are denied.
- Public inquiry submission can still be spammed because Firestore Rules do not provide rate limiting. Enable App Check before public launch; monitor usage and set billing alerts.
- Admin query ordering and public query ordering use existing single-field indexes. The new subscriptions add no compound query. Rules syntax loaded successfully in the local Firestore Emulator and the rules deployment completed successfully on 2026-10-25. Index behavior and the provisioned admin role still need verification against the actual app.

## Homepage content authorization review

- Public list query for `homeExpertise` requires `published == true`; draft records cannot be queried anonymously.
- Public access to `siteSections/homeExpertise` is a single document get and is allowed only when `published == true`.
- Anonymous create/update/delete on both new paths are denied. Admin writes must pass the validators for both create and update; updates preserve `createdAt`.
- Validators bound every string, require secure Cloudinary image URLs for cards, and reject additional fields that are not part of the simplified editor.
- Large input, unknown keys, invalid field types, non-admin writes, and unpublished public queries are rejected by rule conditions. These outcomes were reviewed against rule expressions, not exercised as emulator authorization assertions. Runtime checks against the production project's existing admin role were not run.

## Schema alignment

Current rules match the frontend import/editor fields: project text and Cloudinary URLs; category name/slug/description; client name/website/logo URL; testimonial name/role/location/quote/rating; home expertise; and About tourism name/location/description/photo/order. Inquiry documents contain name/email/phone/project type/location/budget/message/status/timestamps. Image binaries are stored in Cloudinary, not Firestore.
